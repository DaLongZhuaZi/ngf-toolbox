## 真机验证回路（**每轮必做**，2026-10-16 起）

本机**连着真机**，所以「交活前跑一次真编译」不够——必须装上去看。

```bash
# 设备（nova 12 Ultra，就是开发者截图那台；另一台 MatePad Mini 是平板）
HDC='G:/DevEco Studio 26/DevEco Studio/sdk/default/openharmony/toolchains/hdc.exe'
T=192.168.5.124:44879

hdc -t $T install -r entry/build/default/outputs/default/entry-default-signed.hap
hdc -t $T shell aa force-stop com.dlzz.ngftoolbox
hdc -t $T shell aa start -a EntryAbility -b com.dlzz.ngftoolbox
sleep 6
hdc -t $T shell snapshot_display -f /data/local/tmp/s.jpg
hdc -t $T file recv /data/local/tmp/s.jpg ./_s.jpg     # 然后用 read_image 看

# 模拟点击（坐标是**物理像素**，截图宽高就是坐标系）
hdc -t $T shell uinput -T -c 196 1060

# 日志（应用侧域是 A01F00；框架 logger 的 tag 就是类名）
hdc -t $T shell "hilog -x | grep A01F00 | tail -40"
```

**为什么必须做**：十道门禁全绿的情况下，本仓真机上连续出现过——
首页整块空白、工具页没有返回按钮、历史按钮被裸 `{ }` 块吞掉、
状态栏不沉浸、搜索框被顶栏背景压住。**这些没有任何一道门禁能发现。**

> 回报问题时**先截图再改**。凭想象改的每一轮都是浪费。

**⚠️ 坐标必须程序检测，不许看着缩放预览图估。**
实测三次点空，其中一次差了 **420px**（以为输入框在 y=1230，实际 1650）：

- `ⓘ` 关于入口：估 y=641，实际 **692**（图标只有 74px 高，差了 51px 就点到外面）
- 编码套件的输入框：估 y=1230，实际 **1650**
- 键盘弹出后布局会上移，同一坐标会落到别的控件上（点『转换』点到了『解码』）

**做法**：用 `tools/device/ui.py`——它调设备自带的 `uitest dumpLayout`
导出**控件树**（JSON，含每个节点的 `text` 与 `bounds`），**按文字找控件**，
坐标是设备自己报的，不用猜。

```bash
python tools/device/ui.py dump          # 列出所有带文字的控件及其坐标
python tools/device/ui.py tap "转换"     # 按文字点击
python tools/device/ui.py input "abc"   # 往当前焦点输入
python tools/device/ui.py key back      # 返回键
```

**键盘一弹出，坐标就全变了——输入后必须重新 dump。**
实测：`摘要计算` 页点输入框打字后，主按钮从 y=1261 移到 **y=1192**，
用旧坐标会点到别处。正确顺序是「点输入框 → 输入 → **重新 dump** → 按新坐标点按钮」。

**✅ 滚动可用（第 41 轮推翻旧结论）——前提是先收键盘。**

**旧结论（错，已作废）**：「滚动不可用，验证口径就是只验首屏」。
理由是滑动会被系统当成**滑行输入**，往已聚焦的输入框敲进一个字符。
实测确实如此：

```
{"b":2,"a":1}  --滑动-->  {"b":2,"a":1%}      ✗ 键盘弹着时滑动 = 打字
```

**但那不是"滚动不可用"，是"键盘弹着时不能滑"。** 正确顺序：

```
1 点输入框 → 打字
2 按 BACK 收键盘          ← 键盘开着时 BACK 只收键盘，**不会弹掉页面**（实测 页面上:True）
3 滑动 → 页面正常滚动，**输入框不再被污染**
```

实测滚动前后（`JSON 工具`）：

| 控件 | 滑动前 y | 滑动后 y |
|---|---|---|
| 输入框 | 1036 | 276 |
| 缩进选项 | 1406 | 469 |
| 格式化/压缩/校验 | 1649 | 713 |

**内容整体上移 ~930px，且 `field()` 回读值不变。**

> **这条错误的代价**：它让「只验首屏」成了 30 多轮的默认口径——
> 于是**所有输出区在首屏以下的工具都没验过**（JSON/正则/文本 Diff 的格式化结果、
> 端口测试的连通结果、时间戳的日期换算…）。**而它们本来是可以验的。**
>
> **根因还是同一个**：把「键盘弹着时的现象」当成了「滚动这件事的性质」，
> 而且**从未试过先收键盘再滑**。

**⚠️ 别用返回键收键盘（这条仍成立，但要说准）**：**键盘没开着时** BACK 是「返回上一页」，
会把工具页弹掉（实测踩过，看起来像「工具打不开」）。**键盘开着时** BACK 只收键盘，安全。
所以顺序是「**先确认键盘状态，再决定按不按 BACK**」。

。

**验证到位的样子**（两个真机实测例）：
`进制转换` 输入 255、目标 16 进制 → 结果 `0xff`；
`摘要计算` 输入 `abc` → MD5 `90015098 3cd24fb0 d6963f7d 28e17f72`。
**都是可对标准答案的**——「界面渲染出来了」不算验证通过。

**⚠️ 特殊字符在设备端无法可靠输入——靠输入驱动的工具验不了。**

| 输入 | 实际落进输入框 |
|---|---|
| `#FF0000` | **什么都没进**（`#` 被设备 shell 当注释） |
| `{` | `{}` ← **自动补了一个右花括号** |
| `}` | `}` ✓ |
| `{a}` | `{a}` ✓ |
| `abc` | `abc` ✓ |
| `{"b":2,"a":1}` | `{"b":2,"a":1}}` ← 自动补的 `}` 和手打的最后一个撞在一起 |

**根因是设备输入法对「落单的左花括号」自动配对**，不是 shell 引号问题，也不是工具的 bug。
（为此换过三种引号写法、甚至用 base64 解码穿过 shell 绕开引号——**都无效，因为根本不是引号的事**。）
**绕法（2026-10-16 更正，更准确）**：输入法补的 `}` **正好是你要的收尾符**，
而且**光标落在 `{}` 中间**——所以：

```
打 "{"            →  "{}"   （光标在中间）
接着打 '"b":2,"a":1'  →  '{"b":2,"a":1}'   ✓ 完整！
```

**不是「要绕开它」，而是「让它替你打收尾符」。** 之前写成「不要再打收尾的 `}`」
只说了不要做什么，没说**该怎么办**——于是我在下一轮又去打了一次收尾的 `}`，撞出 `}}`。

**⚠️ 退格在这里帮倒忙**：光标在 `{}` 中间时按退格，删掉的是**左边的 `{`**，剩下 `}`。
（实测 `{}` --退格--> `}`。）所以**打完 `{` 就直接往后打，不要退格、不要补 `}`**。

**已知够不到的**：JSON 工具的**输出区在首屏以下**，
所以即使输入对了，`格式化/压缩/校验` 的**结果或报错都看不到**（滑动会污染输入框）。
JSON 工具的**功能结果本回路仍验不了**——但输入这一环现在是通的。

**结论**：`JSON 工具`、`正则测试`、`文本 Diff` 这几件**必须靠人打字输入**
的工具，**本回路验不了**，如实标注「未验证」，不要用坏输入去试然后误判成工具缺陷。
**改完输入一律回读确认**（`field_text()`），这条已经救过一次误判。

**⚠️ `ui.py input` 的命令要加引号**：`#` 在**设备端 shell** 里是注释符，
不加引号时 `uinput -K -t "#FF0000"` 会被截断成空命令，**文字静默不输入**。
看起来像「输入框不工作」，实际是命令没送达。已修成 `uinput -K -t '#FF0000'`。

**真机验出来的一个真实症状（已修，但根因未查实）**：`颜色转换` 打开后挂着红字
「认不出这个写法」，而输入框里是一个合法值 `#0962F2`——两者对不上。

复现路径是「粘进坏值 → 离开 → 再打开」：草稿把那份解析不了的原文带了回来。

⚠️ **但根因没有完全查实，写进注释时也不要写成查实了的样子。**
当时的推理是「出错时输入框显示的是上一次解析成功的颜色」——**这是错的**：
那个三元函数叫 `inputForPreview()`，管的是**预览背景色**，不是输入框；
`TextInput({ text: this.input })` 用的就是原文，本该显示那份坏草稿。
所以「草稿是坏值」能解释红字，解释不了输入框为什么显示合法值。

已做的是**消除症状**（真机验证：红字消失、四种表示形式照常输出）。规则本身成立：
**草稿必须能解析才恢复**（`if (saved.length > 0 && parseColor(saved).ok)`）——
草稿的意义是「恢复没做完的活」，恢复一份解析不了的原文只会让用户一打开就吃一个自己没造成的错。

> 教训：**排查到一半时写下的因果链，会把「猜测」固化成「结论」**。
> 我在同一个会话里已经因为「注释描述了一个没实现的意图」（`ToolStateStore` 测试）
> 白排查过一轮，这次又差点重犯。**写不确定的事，就把不确定写出来。**

### 3.4.3 真机验出来的第二类缺陷：占位符没被填（已修，2026-10-16）

**症状**：`日期计算` 输入非法日期后，报错文案里直接显示出字面的 `%s`：

```
起始日期：无法识别的日期格式：%s（可用 2024-02-29 / 2024/2/29 / 20240229）
```

**根因**：资源串带 `%s` 占位符，消息层却用了**不格式化的** `ToolUiKit.text()`：

```ts
// ❌ 占位符不会被替换
return ToolUiKit.text($r('app.string.date_err_unrecognized'));
// ✅ 带参数的资源必须走 stringOf（同文件其它分支都是这么写的）
return ToolUiKit.stringOf($r('app.string.date_err_unrecognized'), [args[0]]);
```

而且纯逻辑侧也没把「出错的那段文本」带出来（`failure(..., [])`），一并补成 `[text]`。
全仓排查后共 **2 处**（`date_err_unrecognized`、`date_err_non_digit`），都在 `DateCalcMessages.ets`。

**修完真机验证**：
```
修复前：起始日期：无法识别的日期格式：%s（可用 …）
修复后：起始日期：无法识别的日期格式：2026-10-16not-a-date（可用 …）
```

> **为什么十道门禁没抓到**：键存在、三表对齐、代码也能编译——
> 这是一个**运行期格式化**问题，静态检查天然看不见。

> **⚠️ 想给它加门禁，但没加成（如实记录）**：写了「资源含 %s 却用 text()」的检查，
> **变异验证（故意改回 text()）报退出码 0**——是假检查。两次尝试分别栽在：
> ① 块插在了 `process.exit(0)` **之后**，干净跑时根本不执行；
> ② 修好位置后仍不生效（未查明，疑似 `walk`/`stripComments` 的配合问题）。
> **已把这段检查整体删掉**——按本仓规矩，**一条永远通过的门禁比没有门禁更糟**。
> 下次要加，先写一个能跑通的独立脚本，通过变异验证后再并进门禁。

### 3.4.4 ✅ 退格键码是 **2055**（2026-10-16 更正——错用了 37 轮的 67）

**OpenHarmony 的 `KEYCODE_DEL` 是 2055**，不是 Android 的 67。

```
uinput -K -d 67   -u 67    → 删不掉任何字符（错）
uinput -K -d 2055 -u 2055  → 'json' → 'jso'  ✓
```

**代价**：我用了 37 轮错误的键码，期间把「清空输入框」当成做不到的事——
于是有了一整套绕法（用工具的「清空」按钮、重启工具页、只验首屏），
还把这些绕法当成**永久限制**写进了规范（本来的 §3.4.4 就写着「正确做法是用工具的『清空』按钮」）。

**实际上一行 `-d 2055` 就能清空任意输入框。**

> **教训**：一个「不工作」的结论，如果从来没被**反向验证**过（"有没有别的键码能用？"），
> 它就只是一个**未被证伪的假设**——而它会静悄悄地限制后面所有工作。
> 这条在规范里躺了 37 轮，直到要验「搜索清空」时非用不可，才被推翻。

### 3.4.4.1 ⚠️ `uinput -K` 的两个前提：**焦点** 与 **延时**

第 37 轮找到正确键码 2055 之后，又踩了两下才真正能用：

**① 键事件发给「当前有焦点的控件」——没焦点就是打空。**
刚启动应用时输入框**没有焦点**，直接连发退格**一个字符都删不掉**，
而且**不报错**（看起来像"键码又错了"）。
必须**先 `uinput -T -c` 点一下输入框**，再发键。
这也是「重启工具页绕过键盘遮挡」那条（§3.4.7）的代价：
重启后草稿在、键盘不在，**但焦点也没了**。

**② 连发会被丢，必须逐次加延时。**
实测 `for _ in range(30): uinput -K -d 2055`（无延时）→ 21 字符只删掉 17 个；
加 `time.sleep(0.35)` 后仍然接近（25 次删掉 21 个）。

**可用写法**：
```python
focus_input()                       # 先点一下输入框
for _ in range(len(v) + 4):
    ui.sh("shell", "uinput", "-K", "-d", "2055", "-u", "2055")
    time.sleep(0.35)                # 不加延时会丢键
```
**并且删完必须回读确认**（`field()`）——这是唯一能发现"少删了几个"的办法。

### 3.4.5 ⚠️ 键盘会盖住页面按钮，`dumpLayout` 把键盘键也报成节点

在 `端口测试` 页输入目标后，我以为「没有主按钮」（页面上半部只有输入框和提示）。
实际是**键盘弹着，页面按钮被压在下面**；而 dump 出来的 `Stack (920,1802)` 等
**是键盘自己的按钮**——点下去触发了语音输入（页面变成「语音转文字中…」）。

**规则**：
- 找按钮前**先确认键盘已收起**（`keyboard_is_up()`），否则找到的是键盘的键。
- 页面按钮「找不到」时，先怀疑**被键盘挡住了**，不要急着断定「这工具没有主按钮」。

### 3.4.6 ⚠️ 多行输入是 `TextArea`，不是 `TextInput`

### 3.4.8 静态核对占位符数量：**没做成**（如实记录）

想查「`stringOf(资源, [参数])` 的参数个数与资源里 `%s` 的个数是否一致」
（`%s` 缺陷的同类）。写了脚本，跑出来 8+ 条「不匹配」，**逐条核实后发现全是误报**：

```
jwt_status_expired = 已过期：%s（%s）      资源 2 个占位符
  调用 [claimTimeText(decoded.claims[0]), claimRelativeText(...)]   ← 确实 2 个 ✓
cron_hours = %s 点                        资源 1 个占位符
  调用 [numberList(values, true)]          ← 确实 1 个 ✓
```

**根因**：我用 `argList.split(',').length` 数参数——那是**数逗号**。
`numberList(values, true)` 里的逗号被算成了一个额外参数；
`claims[0]` 里的 `]` 又把正则截断。**要数对必须真解析，不能靠数逗号。**

脚本**已删除**——误报的检查比没有检查更浪费时间（要逐条人工核实）。
记录在此，免得下次有人再写一遍同样的东西。

### 3.4.8.5 ✅ **智能引号**：`uinput` 的引号被当字符输入（**已修**，第 48–49 轮）

**症状**：第 46–48 轮 `open_tool` 一直打不开工具，报「搜索框回读=''」——
**错误信息完全指错方向**，我为此猜了三轮（改页签、滚到顶、焦点守卫、直接找 TextInput 节点）。

**根因（把中间状态打出来才看见）**：

```
输入 'json' 后回读:  " ‘json'’"      ← 值里多了两个**弯引号**
```

**修法**：`sh(*args)` 本来就是 `subprocess.run([HDC, "-t", TARGET, *args])`——
**每个 arg 是独立 argv，设备 shell 不会把内容当语法解析**。
所以文本**直接作为独立参数**给即可：

```python
ui.sh("shell", "uinput", "-K", "-t 'json'")   # ✗ 引号被当字符打进去，还变弯引号
ui.sh("shell", "uinput", "-K", "-t", "json")  # ✓
```

**已落地**：`ui.type_text(text)`（独立 argv）+`cmd_input()` 改走它。
`toolkit.py` 里所有输入点都改用 `ui.type_text()`。

**实测**：`ui.type_text("json")` → 回读 `'json'` ✓ **干净**。

> **旧注释的因果链是错的**：`cmd_input` 原注释写着「必须在设备侧 shell 里加单引号，
> 不加的话 `#` 会被当成注释」——**那描述的是一个不存在的问题**（argv 传递不经过 shell 解析），
> 而它引入的引号带来了**真实的问题**。注释已留档纠正。
>
> **教训**：注释里的因果链若前提是错的，会长期误导（同 §3.4 里「草稿是坏值」那次）。

**⚠️ 但 `open_tool` 仍未跑通**（第 49 轮）：`type_text` 单独测是好的，
`open_tool` 里仍报「搜索框回读=''」。**已修的是根因之一，不是全部**——
下一步仍是**把 `open_tool` 内部的中间状态打出来看**（这次别再猜）。

|---|---|---|

> 于是**所有输出区在首屏以下的工具都没验过**（JSON/正则/文本 Diff 的格式化结果、

**验证到位的样子**（两个真机实测例）：
`进制转换` 输入 255、目标 16 进制 → 结果 `0xff`；
`摘要计算` 输入 `abc` → MD5 `90015098 3cd24fb0 d6963f7d 28e17f72`。
**都是可对标准答案的**——「界面渲染出来了」不算验证通过。

**⚠️ 特殊字符在设备端无法可靠输入——靠输入驱动的工具验不了。**

| 输入 | 实际落进输入框 |
|---|---|
| `#FF0000` | **什么都没进**（`#` 被设备 shell 当注释） |
| `{` | `{}` ← **自动补了一个右花括号** |
| `}` | `}` ✓ |
| `{a}` | `{a}` ✓ |
| `abc` | `abc` ✓ |
| `{"b":2,"a":1}` | `{"b":2,"a":1}}` ← 自动补的 `}` 和手打的最后一个撞在一起 |

**根因是设备输入法对「落单的左花括号」自动配对**，不是 shell 引号问题，也不是工具的 bug。
（为此换过三种引号写法、甚至用 base64 解码穿过 shell 绕开引号——**都无效，因为根本不是引号的事**。）
**绕法（2026-10-16 更正，更准确）**：输入法补的 `}` **正好是你要的收尾符**，
而且**光标落在 `{}` 中间**——所以：

```
打 "{"            →  "{}"   （光标在中间）
接着打 '"b":2,"a":1'  →  '{"b":2,"a":1}'   ✓ 完整！
```

**不是「要绕开它」，而是「让它替你打收尾符」。** 之前写成「不要再打收尾的 `}`」
只说了不要做什么，没说**该怎么办**——于是我在下一轮又去打了一次收尾的 `}`，撞出 `}}`。

**⚠️ 退格在这里帮倒忙**：光标在 `{}` 中间时按退格，删掉的是**左边的 `{`**，剩下 `}`。
（实测 `{}` --退格--> `}`。）所以**打完 `{` 就直接往后打，不要退格、不要补 `}`**。

**已知够不到的**：JSON 工具的**输出区在首屏以下**，
所以即使输入对了，`格式化/压缩/校验` 的**结果或报错都看不到**（滑动会污染输入框）。
JSON 工具的**功能结果本回路仍验不了**——但输入这一环现在是通的。

**结论**：`JSON 工具`、`正则测试`、`文本 Diff` 这几件**必须靠人打字输入**
的工具，**本回路验不了**，如实标注「未验证」，不要用坏输入去试然后误判成工具缺陷。
**改完输入一律回读确认**（`field_text()`），这条已经救过一次误判。

**⚠️ `ui.py input` 的命令要加引号**：`#` 在**设备端 shell** 里是注释符，
不加引号时 `uinput -K -t "#FF0000"` 会被截断成空命令，**文字静默不输入**。
看起来像「输入框不工作」，实际是命令没送达。已修成 `uinput -K -t '#FF0000'`。

**真机验出来的一个真实症状（已修，但根因未查实）**：`颜色转换` 打开后挂着红字
「认不出这个写法」，而输入框里是一个合法值 `#0962F2`——两者对不上。

复现路径是「粘进坏值 → 离开 → 再打开」：草稿把那份解析不了的原文带了回来。

⚠️ **但根因没有完全查实，写进注释时也不要写成查实了的样子。**
当时的推理是「出错时输入框显示的是上一次解析成功的颜色」——**这是错的**：
那个三元函数叫 `inputForPreview()`，管的是**预览背景色**，不是输入框；
`TextInput({ text: this.input })` 用的就是原文，本该显示那份坏草稿。
所以「草稿是坏值」能解释红字，解释不了输入框为什么显示合法值。

已做的是**消除症状**（真机验证：红字消失、四种表示形式照常输出）。规则本身成立：
**草稿必须能解析才恢复**（`if (saved.length > 0 && parseColor(saved).ok)`）——
草稿的意义是「恢复没做完的活」，恢复一份解析不了的原文只会让用户一打开就吃一个自己没造成的错。

### 3.4.3 真机验出来的第二类缺陷：占位符没被填（已修，2026-10-16）

而且纯逻辑侧也没把「出错的那段文本」带出来（`failure(..., [])`），一并补成 `[text]`。

### 3.4.4 ✅ 退格键码是 **2055**（2026-10-16 更正——错用了 37 轮的 67）

```

uinput -K -d 2055 -u 2055  → 'json' → 'jso'  ✓
```

**实际上一行 `-d 2055` 就能清空任意输入框。**

> **教训**：一个「不工作」的结论，如果从来没被**反向验证**过（"有没有别的键码能用？"），
> 它就只是一个**未被证伪的假设**——而它会静悄悄地限制后面所有工作。

### 3.4.4.1 ⚠️ `uinput -K` 的两个前提：**焦点** 与 **延时**

第 37 轮找到正确键码 2055 之后，又踩了两下才真正能用：

**① 键事件发给「当前有焦点的控件」——没焦点就是打空。**
刚启动应用时输入框**没有焦点**，直接连发退格**一个字符都删不掉**，
而且**不报错**（看起来像"键码又错了"）。
必须**先 `uinput -T -c` 点一下输入框**，再发键。
这也是「重启工具页绕过键盘遮挡」那条（§3.4.7）的代价：
重启后草稿在、键盘不在，**但焦点也没了**。

**② 连发会被丢，必须逐次加延时。**
实测 `for _ in range(30): uinput -K -d 2055`（无延时）→ 21 字符只删掉 17 个；
加 `time.sleep(0.35)` 后仍然接近（25 次删掉 21 个）。

**可用写法**：
```python
focus_input()                       # 先点一下输入框
for _ in range(len(v) + 4):
    ui.sh("shell", "uinput", "-K", "-d", "2055", "-u", "2055")
    time.sleep(0.35)                # 不加延时会丢键
```
**并且删完必须回读确认**（`field()`）——这是唯一能发现"少删了几个"的办法。

### 3.4.5 ⚠️ 键盘会盖住页面按钮，`dumpLayout` 把键盘键也报成节点

### 3.4.8 静态核对占位符数量：**没做成**（如实记录）

想查「`stringOf(资源, [参数])` 的参数个数与资源里 `%s` 的个数是否一致」
（`%s` 缺陷的同类）。写了脚本，跑出来 8+ 条「不匹配」，**逐条核实后发现全是误报**：

```

  调用 [claimTimeText(decoded.claims[0]), claimRelativeText(...)]   ← 确实 2 个 ✓
cron_hours = %s 点                        资源 1 个占位符
  调用 [numberList(values, true)]          ← 确实 1 个 ✓
```

**根因**：我用 `argList.split(',').length` 数参数——那是**数逗号**。
`numberList(values, true)` 里的逗号被算成了一个额外参数；
`claims[0]` 里的 `]` 又把正则截断。**要数对必须真解析，不能靠数逗号。**

脚本**已删除**——误报的检查比没有检查更浪费时间（要逐条人工核实）。
记录在此，免得下次有人再写一遍同样的东西。

### 3.4.8.5 ✅ **智能引号**：`uinput` 的引号被当字符输入（**已修**，第 48–49 轮）

**症状**：第 46–48 轮 `open_tool` 一直打不开工具，报「搜索框回读=''」——
**错误信息完全指错方向**，我为此猜了三轮（改页签、滚到顶、焦点守卫、直接找 TextInput 节点）。

**根因（把中间状态打出来才看见）**：

```
输入 'json' 后回读:  " ‘json'’"      ← 值里多了两个**弯引号**
```

**修法**：`sh(*args)` 本来就是 `subprocess.run([HDC, "-t", TARGET, *args])`——
**每个 arg 是独立 argv，设备 shell 不会把内容当语法解析**。
所以文本**直接作为独立参数**给即可：

```python
ui.sh("shell", "uinput", "-K", "-t 'json'")   # ✗ 引号被当字符打进去，还变弯引号
ui.sh("shell", "uinput", "-K", "-t", "json")  # ✓
```

**已落地**：`ui.type_text(text)`（独立 argv）+`cmd_input()` 改走它。
`toolkit.py` 里所有输入点都改用 `ui.type_text()`。

**实测**：`ui.type_text("json")` → 回读 `'json'` ✓ **干净**。

> **旧注释的因果链是错的**：`cmd_input` 原注释写着「必须在设备侧 shell 里加单引号，
> 不加的话 `#` 会被当成注释」——**那描述的是一个不存在的问题**（argv 传递不经过 shell 解析），
> 而它引入的引号带来了**真实的问题**。注释已留档纠正。
>
> **教训**：注释里的因果链若前提是错的，会长期误导（同 §3.4 里「草稿是坏值」那次）。

**⚠️ 但 `open_tool` 仍未跑通**（第 49 轮）：`type_text` 单独测是好的，
`open_tool` 里仍报「搜索框回读=''」。**已修的是根因之一，不是全部**——
下一步仍是**把 `open_tool` 内部的中间状态打出来看**（这次别再猜）。

| `{` | `{}` ← **自动补了一个右花括号** |
| `}` | `}` ✓ |
| `{a}` | `{a}` ✓ |
| `abc` | `abc` ✓ |
| `{"b":2,"a":1}` | `{"b":2,"a":1}}` ← 自动补的 `}` 和手打的最后一个撞在一起 |

**绕法（2026-10-16 更正，更准确）**：输入法补的 `}` **正好是你要的收尾符**，
而且**光标落在 `{}` 中间**——所以：

```
打 "{"            →  "{}"   （光标在中间）
接着打 '"b":2,"a":1'  →  '{"b":2,"a":1}'   ✓ 完整！
```

**不是「要绕开它」，而是「让它替你打收尾符」。** 之前写成「不要再打收尾的 `}`」
只说了不要做什么，没说**该怎么办**——于是我在下一轮又去打了一次收尾的 `}`，撞出 `}}`。

（实测 `{}` --退格--> `}`。）所以**打完 `{` 就直接往后打，不要退格、不要补 `}`**。

**改完输入一律回读确认**（`field_text()`），这条已经救过一次误判。

**⚠️ `ui.py input` 的命令要加引号**：`#` 在**设备端 shell** 里是注释符，

所以「草稿是坏值」能解释红字，解释不了输入框为什么显示合法值。

草稿的意义是「恢复没做完的活」，恢复一份解析不了的原文只会让用户一打开就吃一个自己没造成的错。

### 3.4.4 ✅ 退格键码是 **2055**（2026-10-16 更正——错用了 37 轮的 67）

**OpenHarmony 的 `KEYCODE_DEL` 是 2055**，不是 Android 的 67。

```
uinput -K -d 67   -u 67    → 删不掉任何字符（错）
uinput -K -d 2055 -u 2055  → 'json' → 'jso'  ✓
```

**代价**：我用了 37 轮错误的键码，期间把「清空输入框」当成做不到的事——
于是有了一整套绕法（用工具的「清空」按钮、重启工具页、只验首屏），
还把这些绕法当成**永久限制**写进了规范（本来的 §3.4.4 就写着「正确做法是用工具的『清空』按钮」）。

**实际上一行 `-d 2055` 就能清空任意输入框。**

> **教训**：一个「不工作」的结论，如果从来没被**反向验证**过（"有没有别的键码能用？"），
> 它就只是一个**未被证伪的假设**——而它会静悄悄地限制后面所有工作。
> 这条在规范里躺了 37 轮，直到要验「搜索清空」时非用不可，才被推翻。

### 3.4.4.1 ⚠️ `uinput -K` 的两个前提：**焦点** 与 **延时**

第 37 轮找到正确键码 2055 之后，又踩了两下才真正能用：

**① 键事件发给「当前有焦点的控件」——没焦点就是打空。**
刚启动应用时输入框**没有焦点**，直接连发退格**一个字符都删不掉**，
而且**不报错**（看起来像"键码又错了"）。
必须**先 `uinput -T -c` 点一下输入框**，再发键。
这也是「重启工具页绕过键盘遮挡」那条（§3.4.7）的代价：
重启后草稿在、键盘不在，**但焦点也没了**。

**② 连发会被丢，必须逐次加延时。**
实测 `for _ in range(30): uinput -K -d 2055`（无延时）→ 21 字符只删掉 17 个；
加 `time.sleep(0.35)` 后仍然接近（25 次删掉 21 个）。

**可用写法**：
```python
focus_input()                       # 先点一下输入框
for _ in range(len(v) + 4):
    ui.sh("shell", "uinput", "-K", "-d", "2055", "-u", "2055")
    time.sleep(0.35)                # 不加延时会丢键
```
**并且删完必须回读确认**（`field()`）——这是唯一能发现"少删了几个"的办法。

### 3.4.5 ⚠️ 键盘会盖住页面按钮，`dumpLayout` 把键盘键也报成节点

### 3.4.8 静态核对占位符数量：**没做成**（如实记录）

想查「`stringOf(资源, [参数])` 的参数个数与资源里 `%s` 的个数是否一致」
（`%s` 缺陷的同类）。写了脚本，跑出来 8+ 条「不匹配」，**逐条核实后发现全是误报**：

```

  调用 [claimTimeText(decoded.claims[0]), claimRelativeText(...)]   ← 确实 2 个 ✓
cron_hours = %s 点                        资源 1 个占位符
  调用 [numberList(values, true)]          ← 确实 1 个 ✓
```

**根因**：我用 `argList.split(',').length` 数参数——那是**数逗号**。
`numberList(values, true)` 里的逗号被算成了一个额外参数；
`claims[0]` 里的 `]` 又把正则截断。**要数对必须真解析，不能靠数逗号。**

脚本**已删除**——误报的检查比没有检查更浪费时间（要逐条人工核实）。
记录在此，免得下次有人再写一遍同样的东西。

### 3.4.8.5 ✅ **智能引号**：`uinput` 的引号被当字符输入（**已修**，第 48–49 轮）

**症状**：第 46–48 轮 `open_tool` 一直打不开工具，报「搜索框回读=''」——
**错误信息完全指错方向**，我为此猜了三轮（改页签、滚到顶、焦点守卫、直接找 TextInput 节点）。

**根因（把中间状态打出来才看见）**：

```
输入 'json' 后回读:  " ‘json'’"      ← 值里多了两个**弯引号**
```

**修法**：`sh(*args)` 本来就是 `subprocess.run([HDC, "-t", TARGET, *args])`——
**每个 arg 是独立 argv，设备 shell 不会把内容当语法解析**。
所以文本**直接作为独立参数**给即可：

```python
ui.sh("shell", "uinput", "-K", "-t 'json'")   # ✗ 引号被当字符打进去，还变弯引号
ui.sh("shell", "uinput", "-K", "-t", "json")  # ✓
```

**已落地**：`ui.type_text(text)`（独立 argv）+`cmd_input()` 改走它。
`toolkit.py` 里所有输入点都改用 `ui.type_text()`。

**实测**：`ui.type_text("json")` → 回读 `'json'` ✓ **干净**。

> **旧注释的因果链是错的**：`cmd_input` 原注释写着「必须在设备侧 shell 里加单引号，
> 不加的话 `#` 会被当成注释」——**那描述的是一个不存在的问题**（argv 传递不经过 shell 解析），
> 而它引入的引号带来了**真实的问题**。注释已留档纠正。
>
> **教训**：注释里的因果链若前提是错的，会长期误导（同 §3.4 里「草稿是坏值」那次）。

**⚠️ 但 `open_tool` 仍未跑通**（第 49 轮）：`type_text` 单独测是好的，
`open_tool` 里仍报「搜索框回读=''」。**已修的是根因之一，不是全部**——
下一步仍是**把 `open_tool` 内部的中间状态打出来看**（这次别再猜）。

**动机**：`%s` 那个缺陷是走错误路径撞出来的，而 16 件工具的**错误提示几乎没人看过**。
单测断言的是**错误码**，不是**用户看到的那句话**——中间隔着一层消息映射。

走法：`flow.py` 输入明显非法的值（用安全字符，如 `zzz` / `999.999.999.999/40`），读报错。

**已走：**

| 工具 | 输入 | 提示 | 评价 |
|---|---|---|---|
| 进制转换 | `zzz`（10 进制） | 「字符 "z" 不是 10 进制的合法数字」 | ✅ 点名具体字符 + 进制 |
| 子网计算 | `999.999.999.999/40` | 「IP 地址格式不对：需要四段十进制，每段 0~255，且不能有前导零（如 192.168.1.10）」 | ✅ 讲规则 + 给示例 + 提了前导零这个真坑 |

| Cron 解析 | `99 99 * * *` | 「分钟段超出允许范围（0-59）：99」 | ✅ 段名 + 范围 + 越界值，三要素齐全 |
| JWT 解码 | `notatoken`（无点号） | 「JWT 由 3 段组成（Header.Payload.Signature），当前是 1 段。」 | ✅ 讲结构 + 段名 + 实际段数 |
| JWT 解码 | `a.b.c`（非法 base64） | 「Header 段不是合法的 Base64URL：Base64URL 长度不合法（去掉 = 之后余 1 个字符）」 | ✅ 点名哪一段 + 违反了哪条规则 |

**结论（6 件里 5 件好）**：这个代码库的错误文案整体是**照着「用户知道下一步改什么」写的**，
`%s` 那一处更像**孤例**（用了不格式化的取值方式），而不是通病。

**最好的两条**（值得作为本仓文案标准）：
- JWT：「Header 段不是合法的 Base64URL：**长度不合法（去掉 = 之后余 1 个字符）**」

- Cron：「分钟段超出允许范围（0-59）：99」—— 段名 + 范围 + 值。

> 找报错前先确认这页有没有主按钮、点了没有。

> **⚠️ 草稿污染会让报错看起来是错的**：不清空直接输入，字段里是
> `0 9 * * 1-599 99 * * *`——Cron 报「当前是 **9** 段」，看起来像工具数错了段。
> **每次输入前必须清空**（`flow.py` 会做，临时脚本经常忘）。

## 按压反馈不需要自定义（第 130 轮）

尝试给历史列表项加 clickEffect 时发现：ArkUI 可点击组件默认已有按压反馈（系统自带透明度变化）。
自定义 clickEffect 反而要手写 ClickEffect 实例（ArkTS 禁止接口字面量），且偏离系统观感。
结论：不要给可点击组件手写按压态，系统默认即规范。先确认系统已提供什么，再决定是否自定义。

## 3.4.13 装机前的签名自检（第 103 轮踩坑）

**现象**：`build-profile.json5` 里明明有 `signingConfigs`，构建却报 `[WARN] No signingConfig found for product default`，只产出 `entry-default-unsigned.hap`；装设备报 `code:9568320 error: no signature file`。

**根因**：`app.products[0]` 缺 `"signingConfig": "default"` 这一行**引用**。DevEco 的 Signing Configs 面板只写 `signingConfigs` 数组，**不会自动回填 product 的引用**。

**自检三步（装机前必做）**：

1. `signingConfigs` 非空；
2. `products[0]` 有 `"signingConfig": "default"`；
3. 产物文件名带 `-signed`，且 build.ps1 打印「已产出**已签名**包」。

> **教训**：只看到 `signingConfigs` 就断言「签名配好了」是错的——**引用没接上等于没配**。判据必须是产物名。

## 3.4.14 坐标与滑动（第 103 轮校正，此前写反过）

- `uitest dumpLayout` 的 `bounds` **就是 `uinput` 的物理坐标**，直接拿来点，**不要换算**。
- `snapshot_display` 的截图被**缩小保存**（1224x2776，约为物理的 2/3），所以截图位置 **× 1.5 ≈ 物理坐标**；直接拿截图坐标点会落到别的控件上。
- 实测同一元素：截图 y≈1810，dump 报 y=2704 —— **2704 才是能点中的那个**。
- **滑动**用 `uitest uiInput swipe x1 y1 x2 y2 [duration]`；`uinput -T -s x1 y1 x2 y2` 实测**不生效**（页面纹丝不动，且不报错）。

## 3.4.15 悬浮底栏：`barOverlap` ≠ `barFloatingStyle`（第 103 轮）

**用户一句话点破：「它有 HdsTab 的悬浮底栏吗？」——没有。**

首页底部当时就是一行贴着屏幕底边的裸文字，没有容器、没有圆角、没有系统材质背景。而十道门禁全绿、编译无告警、页签能点能切。

**根因**：只写了 `barOverlap(true)`。它只表示「栏压在内容之上」，栏自身仍是**贴边通栏**。真正让它浮起的是：

```ts
.barFloatingStyle(new ToolboxTabFloatingStyle(level))   // 类型来自 @kit.UIDesignKit
```

**正解照来源仓 `MainMenuPage` 抄（只 5 个字段，不要自行发挥）**：

```ts
.barFloatingStyle({
  adaptToHandedness: true,
  systemMaterialEffect: { materialType: IMMERSIVE, materialLevel: <框架视觉设置> },
  thermoCtrl: true,
  barOpacity: 0.95,
  barBottomMargin: this.bottomInsetVp   // 手势条实测高度
})
```

**两条错法本仓都踩过**（第 103 轮同一晚上）：

1. 不写 `barFloatingStyle` → 底部是贴边裸文字。
2. 写了但**自己加 `barHeight(64)`、把 `barBottomMargin` 写死 16** → 栏被撑高、还不躲手势条。

**关键**：**不要设 `barHeight`**（系统默认值就是设计值），`barBottomMargin` 取
`window.getWindowAvoidArea(TYPE_NAVIGATION_INDICATOR)` 的实测高度——本仓直接复用
`ui/WindowChrome.ets` 的 `loadDynamicInsets()` 的 `bottom` 回参（本机实测 **27.85vp**）。

> 判据：改完看栏是否**正好浮在手势条上方**、高度是否与「收藏/网络」这些页签内容贴合。
> 撑高或贴底都是错。

**连带三处（都只有真机能发现）**：

1. **页签没有图标** —— 来源仓 `MainMenuPage.buildTabItem` 是 `SymbolGlyph + Text`，选中时图标 24/加粗、未选 22/常规。只有文字时观感就是「手搓标签栏」。
2. **切页失效** —— 自定义 `.tabBar(@Builder)` 只是展示内容，HdsTabs 不会绑定切换；一旦外层挂 `onTouch`（按压反馈要用），事件被消费，点页签**彻底没反应**。必须在 `TouchType.Up` 里 `this.tabsController.changeIndex(index)`。
3. **底部留白不够** —— `CONTENT_BOTTOM_INSET` 原为 76（来源仓纯文字栏的值）；带图标后栏更高，76 会让最后一排卡片被压住，改 104 后滚动到底完整可见。

> **这一类错误十道门禁一道都查不出**：不是类型错、不是资源缺、不是结构错，纯粹是「框架有能力但没接上」。
