#### 二.2 双语的真实规模（实测，交给下一轮的人）

用「含中文字符的字符串字面量」为口径统计，全仓 `entry/src/main/ets` 共 **1203 处**，
分布在 45 个文件里，最大的几个：

| 文件 | 处数 | 性质 |
| --- | --- | --- |
| `tools/regex-tester/RegexLogic.ets` | 86 | **纯逻辑** |
| `tools/ToolsCatalog.ets` | 77 | 纯数据（工具元数据） |
| `tools/cron-parser/CronParser.ets` | 63 | **纯逻辑** |
| `tools/port-tester/PortTester.ets` | 52 | **纯逻辑** |
| `tools/timestamp/TimestampLogic.ets` | 48 | **纯逻辑** |
| `tools/json-toolkit/JsonLogic.ets` | 46 | **纯逻辑** |
| 其余 39 个文件 | 831 | 混合 |

**关键障碍：约 550 处文案在「纯逻辑」模块里，而那些模块按设计不能 `import` ArkUI。**

`$r('app.string.x')` 是 ArkUI 的资源引用能力，而纯逻辑模块的**存在意义**就是
零设备依赖——这正是它们能在本机跑单测的前提（AGENTS.md §3.1）。
所以「把文案换成资源键」这条最直觉的路，在纯逻辑层**根本走不通**。

而且这些文案不是随便的字符串：它们是**被 573 个用例断言着的错误信息**
（例如「连接被拒绝：主机能到，但这个端口没有服务在监听」）。
直接改文案会让大量测试失败——这本身是个信号：文案已经是**接口的一部分**。

**正确的架构**（也是推荐做法）：

1. 纯逻辑不再返回**成品文案**，而是返回**结构化结果 + 错误码**
   （形如 `class ToolFailure { code: FailureCode; detail: string }`）；
2. 页面层把错误码映射到资源键（`$r('app.string.err_port_refused')`）；
3. 单测改为断言**错误码**而不是断言文案——断言文案本身是脆的，
   一改措辞就要改测试，而错误码是稳定契约。

这样做还有个额外收益：错误码让「同一个原因在不同工具里措辞不一致」的问题
变得可见（现在 16 件工具各写各的，措辞风格其实不统一）。

**推进顺序**（每步都能单独跑绿门禁再进下一步）：

- `code-viewer`：示范了**显示函数下移**。原先 `describeDocument` / `rejectReason`
  住在纯逻辑层却返回拼好的中文句子，这是分层错误：显示逻辑归 UI。
  现在纯逻辑只给零件（行数 / 是否截断 / 是否过大），句子在 `CodeViewerMessages.ets` 组装。
  另外它示范了**专有名词与需翻译名的区分**：`languageLabel` 只给
  「JavaScript / C++ / YAML」这类专名，而「纯文本 / 键值配置」用
  `languageNeedsResource` 标记后走资源键——判断依据是「这个词在别的语言里会不会变」。
- `text-diff`：示范了**「注入文案」而不是「自己拼文案」**。
  `toUnifiedText` 要输出可复制的统一 diff，格式（`---` / `+++` / `@@`）是**数据格式**、
  留在纯逻辑层；但其中那行统计「新增 N 行，删除 M 行」是**文案**，由调用方作为参数传进来。
  这样格式仍可单测，而措辞可多语言。
  它还示范了把 `summarizeDiff` 之类的显示函数拆成**两部分**：
  纯逻辑留「判断」（`hasLineEndingMismatch`、`diffSummaryFacts` 给出的
  `sameLineCountRewrite` 等事实），UI 层负责「措辞」。判断才是容易写错、
  值得单测的部分；措辞改了不该动测试。
- `subnet-calc`：示范了**「标签 + 值」型报告的写法**。
  `formatSubnetReport` 原先在纯逻辑层拼出十行「标签：值」——标签是文案，所以搬到了 UI 层。
  两个细节值得抄：
  ① 连**分隔符**都用资源键（中文「：」、英文「: 」）——标点差异是最容易被漏掉的本地化问题，
     它不是词，所以没人会想到要翻译；
  ② 它把「地址性质」这类**双语数据**（`NGFLocalizedText`）与「页面文案」（资源键）
     放在同一页里共存，正好演示了两种机制的分工边界该怎么划。

  另外这件工具还顺手补了一个**既有缺陷**：`prefixRemark`（前缀常识提示）
  有实现、有单测，但**页面从来没调用过**——提示永远不显示。
  现在接进了「无注意事项时显示前缀说明」的分支，并做成二选一避免与注意事项重复。
- `color-convert`：示范了**把笼统的失败码拆细**。
  原先 11 处失败只用了 5 个码，于是「rgb() 少一个括号」「rgb() 参数个数不对」
  「通道值不是数字」共用一个 `UNKNOWN_FORMAT`/`BAD_CHANNEL`，**话术只能一样**。
  现在拆成 11 个码（`RGB_MISSING_PAREN` / `RGB_ARITY` / `CHANNEL_RANGE` /
  `HEX_BAD_CHAR` / `HSL_PERCENT` …），每种情况都能给对症的提示。
  > 这是做双语时的一个**顺带收益**：为了让文案可翻译，被迫先把「到底失败在哪」
  > 想清楚，结果错误提示本身也变准了。中文单语时这种笼统是可以蒙过去的。

  它还示范了一条**命名纪律**：HEX / RGB / HSL / HSV / CMYK 这些标签**不翻译**
  （国际通用缩写，翻译了反而认不出），只翻译「最接近的颜色名」「建议前景色」
  这类说明性标签。判断依据仍是那条：**这个词在别的语言里会不会变**。
- `date-calc`：示范了**带上下文的失败**。
  间隔计算的失败其实是「某一侧日期解析不了」，所以失败对象是**两层**的：
  外层是「哪一侧」（`DateDiffField`），内层是那一侧为什么不行
  （`DateParseFailure` + 参数）。页面才能拼出「结束日期：无法识别的日期格式」。
  > 反过来说：如果失败只用一句 string 表示，这种做法就没法翻译——
  > 译文里「结束日期：」和后面那句的顺序、标点都可能不同。
  > **把失败结构化，是让它可翻译的前提。**

  它还示范了**解析器字面量的处理**。该工具接受 "2024年2月29日" 这种输入，
  于是源码里有 '年' / '月' / '日' 三个字面量——它们是「别人写给我们看的输入语法」，
  不是「我们写给用户看的文案」，翻译没有意义，但 `check-i18n.mjs` 无法自动区分。
  处置方式是在**同一行**加 `// i18n-parser-literal`，脚本会把它连同 **file:line 与整行内容**
  一起打印出来供复核。刻意要求显式标记 + 全部打印：
  **一个不说话的口子迟早会变成掩盖真实残留的工具。**
- `uuid-password`：示范了**强度/建议用枚举而不是字符串**。
  档位从「很弱/弱/一般/强/很强」改成 `PasswordStrengthLevel`，
  建议从 9 句中文改成 `PasswordAdvice` 码。好处不只是可翻译：
  **测试现在断言「这条密码该给出哪几条建议」，而不是去子串匹配文案**——
  文案改措辞不会让测试变红，而判断被钉住了。

  它同时暴露了一个**潜在 bug**：`toggleClass(label, value)` 用**显示标签本身**
  当逻辑键（`if (label === '小写 abc')`）。中文单语时看不出问题，
  一旦标签被翻译，开关就再也找不到对应字段。已改为 `FIELD_*` 常量。
  > 这是双语改造的一类典型收益：它逼你把「只是文案」和「兼作逻辑键」分开。
  > **凡是拿显示文案当 key 的地方，都是待爆的雷。**
- `timestamp`：示范了**语序差异最极端的一类文案**。
  相对时间「3 分钟前」在中文里是「数量 + 单位 + 后置方向词」，
  英文过去时是 "3 minutes ago"，**未来时却是 "in 3 minutes"（前置介词）**。
  任何拼接方案都会在其中一种语言里读起来别扭，所以纯逻辑只返回
  `RelativeTime { unit, value, past }`，12 句措辞各自是一个完整的资源键。

  它还把「秒/毫秒向下取整」这类**单位换算**（`millisToSeconds`）也收进了纯逻辑，
  页面上原本散着 `Math.floor(nowMs / 1000)`——同一件事写两遍，
  一旦有人改成四舍五入就会两边不一致。
- `qrcode`：示范了**纯逻辑不该回传「已翻译好的显示名」**。
  原先成功结果要带一句 `kindLabel`（「扫出来会被识别成什么」），
  但那句话就是请求里那个 kind 的显示名，**页面本来就知道 kind**。
  让纯逻辑回传一个已经翻译好的字符串，等于把 UI 的活挪进了逻辑层；
  去掉之后页面直接用 `qrResultKindText(this.kind)`，还顺手删掉了一个不再被读的 @State 字段。

  它还示范了**两套名字各自成键**：类型选择器上写「名片」省地方，
  结果里写「联系人名片」更清楚。两处各自是资源键，翻译时能各自取舍——
  硬把一处复用成另一处，就会在某种语言里出现「选择器太啰嗦」或「结果太含糊」。
- `codec-suite`：示范了**示例内容也要国际化，而且必须自洽**。
  页面上每个模式给一段「点一下就能跑通」的示例。原先示例写死中文
  （base64 的示例是 `中文 Base64 😀`），英文环境下举「中文」的例子没有意义。
  改成资源键之后，**英文示例必须与它的编码结果自洽**——
  否则用户点「示例」再点「转换」，得到的是一个报错。
  英文那组是用 Node 现算的（`SGVsbG8gQmFzZTY0IPCfmIA=` 等）。

- `jwt-decoder`：示范了**「错误位置」不该拼进句子**。
  JSON 解析失败要说「第 1 行第 5 列」——中文这样写，英文写 "line 1, column 5"，
  **连标点都不同**。所以位置单独作为参数（`line` / `column`）传出去，
  由 UI 层的资源键决定怎么摆。
  它还示范了**三层嵌套失败**：JWT 段 → Base64URL → JSON，
  `JwtDecodeFailure` 同时带外层码、`b64Code` 与 `jsonCode`。
  > ⚠️ 踩过的坑（下一件做类似改造时注意）：改完 `JwtDecoder.ets` 后
  > `NGFJsonFailure` **用在了值位置却忘了加进 import**。类型位置会被剥掉所以不报错，
  > 只在运行到 `static none()` 时才炸，表现为 13 个用例齐刷刷
  > `NGFJsonFailure is not defined`。**改完纯逻辑要顺手核对新用到的每个枚举都在 import 里。**

- `cron-parser`：示范了**把「句子生成器」拆成结构**。
  它的 `buildDescription` 原先直接拼中文（`'每 5 分钟（9、17 点内）'`）。
  英文不是逐词替换：`Every 5 minutes (during hours 9 and 17)`——量词、连接词、
  括号位置全不同。现在纯逻辑给 `CronDescription { basis, step, hours[], ... }`，
  句式由 UI 层按 `basis` 选，数字原样带出去。

  > ⚠️ 这一轮在**同一个坑里摔了三次**，都是机械替换留下的：
  > ① 改 `CronField` 构造器时**漏传了 `raw`**，后面四个参数整体前移一格——
  >    不报错，只是 `*` 展开出的 `values` 变成空数组，于是任何表达式都算不出执行时间；
  > ② 在调用点写了 `minuteStep.fieldKey`，但 `FieldStep` 根本没有这个属性；
  > ③ `string.json` 超过 2000 行后 `tools.read` 会**截断**，`JSON.parse` 报
  >    `Unexpected end of JSON input`——资源表已过大，**改用 Node `fs` 直接读写**。
  >
  > 教训：**改构造器签名后要逐个核对调用点的参数顺序**（参数错位不报错、只算错），
  > 以及**别引用没确认存在的属性**。

- `regex-tester`：全项目最大的一件（127 处），示范了**改动面大时怎么控制风险**。
  两处特别值得看：
  ① **可复制的文本报告留在纯逻辑里**（`buildMatchReport`），但把「摘要句」和
     「错误句」作为**参数**接收。理由是它的格式（一条匹配一行、换行转义）出错时
     真机上很难稳定复现，必须由单测守住；而句子归 UI 层。**格式一份，句子两套。**
  ② 引擎报错的处理分三档：认识的措辞 → 具体种类；**有原文但对不上号** → `UNKNOWN`
     （UI 连原文一起显示，开发者能自己搜）；连原文都没有 → `PARSE_ERROR`。
     原来这三档塌成一档，「留着线索」的意图在代码里其实没落实。

  > ⚠️ 这一轮暴露了一道门禁的**盲区**：`check-resources.mjs` 把资源表读成 Map，
  > 于是**重复键在读进来的一瞬间就消失了**。
  > 实际后果：`jwt-decoder` 与 `json-toolkit` 撞了 10 个 `json_err_*` 键，
  > 两边都需要这 10 个键但文案不同——先写的永远生效，另一个工具永远显示别人的句子。
  > 不报错、不崩溃、不失败，九道门禁全绿。
  >
  > 已修：检测挪进 `readElementJson` 的原始数组循环里（出了那个函数就再也看不见了），
  > 并**用「故意造一个重复键」自测过它真的会红**。命名为 `jtk_err_*` 完成隔离。
  >
  > 教训：**「字段名能对上」不等于「取到的是我写的那份」**。

- `json-toolkit`：示范了**「位置」与「原因」分两层给出去**。
  解析错误是 `JsonError { code, args, line, column, position }`——
  位置**不进码也不进句子**，因为中文写「第 3 行第 5 列」、英文写 "line 3, column 5"，
  连标点都不同。UI 层先拼位置（`json_error_at`），再套一层
  `json_error_line`（`'%s（%s）'` / `'%s (%s)'`）。
  根节点概要同理：`describeJsonRoot` 从返回句子改成返回 `JsonSummary`，
  测试也从「包含 '2 个键'」变成断言 `kind` 与 `count`。

  它还给 `check-resources.mjs` 的白名单补了正经用例：`Base64` 与 `Hex`
  是技术专名，中英写法相同。门禁报「疑似漏翻译」是**对的**——
  它逼着人写明理由，而不是让「反正它就是一样的」蒙混过去。
  （对照 `codec_mode_url`：「URL 整段」/ 'Full URL'，那个确实会变。）

已完成的工具要登记进该脚本的 `COMPLETED_TOOLS`——一旦回退（新加一句中文提示、
改一处忘了走资源键）立刻判失败。这个守卫是必要的：漏翻译不报错、不崩溃，
现有八道门禁一道都看不出来。

#### 二.3 第 3 步的样板：一件工具要改哪四处

以 `radix-convert` 为例（其他 15 件照抄这个流程，每件一轮）：

1. **纯逻辑加失败码**（`RadixConvert.ets`）：新增 `RadixFailureCode` 枚举与
   `RadixFailure { code, args }`，把原来直接返回的中文句子换成「码 + 参数」。
   两个结果类的 `message: string` 换成 `failure: RadixFailure`，
   并用 `RadixFailure.none()` 兜住成功路径——**永不为 null**，
   这样传递上游失败时不必写判空（`failureOf(parsed.failure)` 直接可用）。
   - 参数里连 `RADIX_MIN`/`RADIX_MAX` 这类常量也要传：让资源文案不必重复写死 2 和 36，
     常量和文案永远一致。
2. **UI 层加映射**（`RadixConvertMessages.ets`，**新文件**）：
   `radixFailureText(failure): ResourceStr`，用 if 链，**每个分支一个字面量 `$r()`**。
   啰嗦是刻意的——`$r` 的键必须是字面量（PR-013），
   而且字面量才能让 `check-resources.mjs` 顺着核对键是否存在。
   - 命名约定：这类文件叫 `*Messages.ets`；`run.mjs --logic` 按
     `(Page|Messages)\.ets` 把它们排除在「纯逻辑」之外。
3. **资源表加文案**（三份 `string.json`）：键名统一带 `err_<tool>_` 前缀，
   文案里用 `%s` 占位，**参数顺序必须与 `failure.args` 一致**。
   这条没有编译期保护，是这套改造里唯一靠人守的地方。
4. **单测改断言错误码**（`RadixConvertTest.test.ets`）：
   `expect(x.message).assertContain('g')` → `expect(x.failure.code).assertEqual(...)`
   +`expect(x.failure.args[0]).assertEqual('g')`。
   断言码比断言文案稳：改措辞不用动测试，而码是契约。

**页面侧**：`*Messages.ets` 返回**已解析好的 `string`**（占位符已代入），
所以页面的错误字段照旧是 `string`、照旧用 `.length > 0` 判断空——
不需要 `ResourceStr`，也不需要额外的布尔量。
（早先试过让映射层返回 `ResourceStr`，那会逼着页面处理联合类型，得不偿失。）

**操作提示**：`tools/edit` 在这类批量替换上偶发「old_string not found」（同内容用 JS 层
`includes` 校验却为真）。遇到时改用「读全文 → JS 字符串替换 → 整篇写回」即可绕过，
本轮的 digest 页面就是这么改完的。别在批量替换失败时怀疑文件内容。

#### 占位符参数走哪条路（已定，别再纠结）

用 `ToolUiKit.stringOf($r('app.string.x'), [args…])`，**不要**用 `$r('app.string.x', args…)`。

- 键仍是**字面量** `$r('app.string.x')`：构建期能静态改写，`check-resources.mjs`
  也能顺着字面量核对键是否存在（PR-013）。
- 占位符的代入交给框架的 `resolveStringWithArgs` → `resourceManager.getStringSync(resource.id, ...args)`。
  这是**框架里已经写好的实现**，社区样例与框架自身都在用，不需要押一个新用法。
- `$r('app.string.x', args…)` 把代入交给 ArkUI 渲染器，本机无法构建验证；
  既然已有可复用且有旁证的实现，就没必要冒险。

`ToolUiKit.stringOf` 的入参类型是 `string | Resource`，因此也接受资源裸名
（`getStringByNameSync` 那条路）——但**同一件工具里只用一种**，别混。

> 做第 3 步时可以照抄第 1、2 步已经验证过的两个套路：
> ① 纯数据层用 `NGFLocalizedText`（别 import ArkUI）；
> ② 给「漏翻译」配一条会失败的断言或门禁，否则它永远不会被发现。

> 现成的护栏：`tools/verify/check-resources.mjs` 会校验
> 「代码引用的资源键是否存在」「base / zh_CN / en_US 三份表是否对齐」，
> 因此第 2、3 步里手写几十上百个键时，拼错和漏写能在本机就发现，不必等 CI。
> `tools/ToolSymbols.ets` 那种「字面量表」模式也适用于文案表（PR-013）。
2. **本地签名**：仓库不含签名材料；首次用 DevEco 打开时配置自动签名即可本地调试。
3. **发布签名 Secrets**：sign-and-release 需在 GitHub 仓库 Secrets 配置签名材料后才会真正签名。
4. **反馈中心 app_id**：关于页目前只有 GitHub Issue / QQ 群 / 邮件三个渠道。
   上架前若要在反馈中心后端注册 `ngftoolbox`，把入口加进 `about/AppInfo.ets` 的
   `feedbackLinks()` 即可（页面会自动多出一行，无需改 UI）。
5. **框架仓 README 快速开始**：在 NGF 来源仓补「如何引入 HAR + 最小示例」，与本仓 README 互链。
6. **版本号**：`AppScope/app.json5` 仍是 0.1.0。是否升版（建议 0.2.0）由开发者决定——
   版本号是发布决策，不在无人确认时自行改动。

## 四点五、输入历史（**已完成**）

`docs/产品定义.md` **第 56 行**要求六项框架级功能「随首发上线」，其中「每个工具的输入历史（data 层）」
原本**完全没有实现**——而 `AGENTS.md` §3 的交互模板与**关于页的隐私声明**都已把它当成已有能力。

现已补齐。规模：**1 个中转模块 + 1 处壳层 UI + 15 件工具接线 + 13 个单测 + 4 个三语键**。

### 分三层，各做各知道的

1. **数据层**（`core/ToolStateStore.ets`）
   三个纯函数 `isHistoryWorthy` / `parseHistory` / `appendHistory`，
   四个常量（上限 10 条、定型 1.5s、最小长度 2、键前缀），
   三个方法 `readHistory(toolId, now)` / `pushHistory` / `clearHistory`。

   **挂在 `writeDraft` 这个唯一漏斗上**（16 件工具、24 个调用点都经过它），
   所以它是**底层能力**而不是页面补丁。「一个值算不算历史」用**惰性时间戳比较**判定——
   读取时看它多久没变过，**不需要在数据层跑定时器**（定时器会随页面销毁泄漏，且本机无法验证）。

2. **中转**（`ui/HistoryPick.ets`）
   本仓结构是「**壳层包着工具体**」，壳层够不着工具体的 `@State`。
   所以回填分两步：壳层把选中的值**写进草稿**（草稿本来就是工具体的输入源），
   再**递增一个 AppStorage 序号**；工具体用
   `@StorageProp(TOOLBOX_HISTORY_PICK_SEQ) @Watch('onHistoryPick')` 订阅序号，变了就重读草稿。

   值**不经过** AppStorage（只有序号经过）——历史里可能存着长文本，而这样也让回填
   复用「草稿恢复」这条既有路径，不必给每件工具再造一套赋值协议。

3. **接线**（15 件工具，每件 5 行）
   `code-viewer` **未接线**：它是「打开本地文件」的查看器，没有文本输入也没有草稿，
   历史对它不适用。

### 自查发现并修掉的两个缺陷（**新功能最容易复发的两类错**）

功能做完、编译通过、门禁全绿之后又自查了一遍逻辑，找出两个**编译期与门禁都看不见**的缺陷：

**缺陷 1：历史会丢。** 最初「定型」判定只在 `readHistory` 里做（打开面板或重进页面时）。
于是这条最常见的路径：

> 输入 `255` → 停一会 → 改成 `65535` → 关掉 app

**`255` 从未被提交，永久丢失**——「最近输入」丢输入，是功能性错误，但**不报错、不失败**。

修法：在 `writeDraft` 里**覆盖草稿之前先结算上一个已定型的值**，
并把这个判定抽成纯函数 `shouldCommitPrevious(lastAt, lastValue, nextText, now)`，
补了 4 个用例覆盖它的三个边界（没有上一个值 / 没定型 / 新旧相同）。

> 为什么要抽成纯函数：这三个边界**都不报错**。漏掉第一个会把空串记成历史，
> 漏掉第二个历史里全是逐字符半成品，漏掉第三个光标来回移动就刷出一堆重复项。

**缺陷 2：历史按钮可见性死锁。** 按钮原本写成「有记录才显示」，
而记录只在 `readHistory` 里产生、`readHistory` 只在打开面板时调用。于是：

> 首次使用没有记录 → 按钮不出现 → 打不开面板 → 永远没有记录

修法：按钮**常显**，空态交给面板里的 `shell_history_empty` 文案承担。

> 教训：**「条件渲染」与「产生该条件的数据」如果互为因果，就会锁死。**
> 写「有 X 才显示入口」之前，先确认「X 的产生路径不需要这个入口」。

### 两个实测踩到的坑

- **`AppStorage` 不要 import**。它是全局对象，不是 `@kit.ArkUI` 的导出成员；
  写成 `import { AppStorage } from '@kit.ArkUI'` 会报
  「has no exported member named 'AppStorage'」。本仓 `pages/Index.ets` 也是直接用全局的。
  （与之前 `WrappedBuilder` 是同一类：**全局类型/对象被当成 import**。）
- **接线脚本的守卫写错了**：我用 `!t.includes("HistoryPick'")` 判断「import 加过没有」，
  而刚插入的 `@Watch('onHistoryPick')` 里**正好含 `HistoryPick'`**，
  于是 import 被跳过 → 15 个文件全部 `Cannot find name`。
  教训与 §2 那条同源：**先引入了名字，再拿这个名字当「有没有做过」的哨兵**。
  正确的哨兵是 `from '../../ui/HistoryPick'`。

### 多输入工具的取舍（**下次改这里先读**）

历史记录的是**每件工具的主草稿**（`TOOL_ID` 那个键），回填也只回填主输入字段：

| 工具 | 主字段 |
|---|---|
| color-convert / codec-suite / digest / json-toolkit / port-tester / radix-convert / subnet-calc / timestamp | `input` |
| cron-parser | `expression` |
| jwt-decoder | `token` |
| qrcode | `payload` |
| regex-tester | `pattern` |
| date-calc | `startText` |

`date-calc` 有 5 个输入框、`text-diff` 有左右两份草稿（`TOOL_ID + '.right'`）。

## 四点十、沉浸式设计缺失修复：**窗口级沉浸从未开启**

### 用户反馈

> 整个 app 的沉浸式设计呢？状态栏不沉浸、操作栏也不沉浸

### 两个独立的原因（都不是「微调」，是**缺失**）

**① 状态栏不沉浸 → 窗口级沉浸从未开启。**

`setWindowLayoutFullScreen` 在全仓 **0 处调用**。ArkUI 默认把窗口布局在**状态栏下方**，
状态栏区域显示的是窗口底色。于是底板的 `expandSafeArea([SYSTEM], [TOP])`
**根本没有可扩展的空间**——无论怎么调底板的高度和配色，状态栏都不会沉浸。

框架把这件事包在 `platformOhos` 层的 `ngfPlatformWindowManagerFacade` 里，
用 `NGFDisplayMode` 选策略（`IMMERSIVE_WITH_BARS` = 布局全屏 + 两条系统栏透明可见）。
**app 一次都没用过这个门面。**

> ⚠️ 这与首版「漏掉整个 uiShell 层」是**同一类错误**，只是换了一层。
> 教训：盘点框架能力时，**非 UI 的层（platformOhos / deviceAwareness）同样要盘**，
> 只盘 UI 层会漏掉「沉浸式」这类横跨窗口与页面的能力。

**② 操作栏不沉浸 → 首页根本没有顶栏。**

`NGFImmersiveTopChromeUnderlay` 只出现在 `ui/ToolScaffold.ets`（工具页）。
`pages/Index.ets`（首页）**一处都没有**——首页顶部就是纯色背景加大标题。

## 五、已知边界与风险（交接时必须知道）

1. **本机无编译验证**：`tools/verify/` 只能验证纯逻辑与页面**结构性**；
   装饰器、ArkUI 属性类型、资源引用仍只能由 CI 构建与真机验证。
2. **时区为固定偏移、不含夏令时**（时间戳工具）：已在工具 limitation 与页内说明。
   `@ohos.intl` 能拿到完整时区库但属设备能力，纯逻辑层不能 import。
3. **JWT 解码不验签**：只解码 Header/Payload 并展示签名段，工具 limitation 已明示。
4. **摘要为手写实现**（框架的 securityToolkit 是 async + 依赖设备能力，纯逻辑层用不了）。
   已用 `cross-verify-hash.mjs` 与 Node crypto 对拍 56 组（含分组填充边界）全一致，
   但**手写密码学实现本身**仍是需要真机/CI 长期留意的风险点。
5. **正则错误文案依赖引擎行为**："at position N" 不保证存在，已用自研
   `analyzePattern` 兜底并单测钉住退化路径（认得就精确、不认得给通用中文文案）。
6. **草稿写入有 800ms 节流**：进程被强杀最多丢 800ms 输入；
   正则草稿做了字段级裁剪，避免被 `ToolStateStore` 的 10 万字符上限截尾破坏 JSON 结构。
7. ~~工具元数据目前只有中文名，英文环境下搜 `Timestamp` 会搜不到。~~
   **已于第三轮修复**：元数据双语 + 搜索同时匹配中英两侧，见 §二.2 第 1 步。
   残留的是**工具内部文案**（字段标签、错误话术、帮助说明）仍为中文，
   那属于 §二.2 第 2、3 步的范围。
8. **平台调用只有 CI 与真机能验证**：二维码绘制（ArkUI `QRCode`）、
   文件选择与读取（`ngfMediaPickerFacade` + `FileUtils`）、TCP 连接（`@kit.NetworkKit`）
   这三处已刻意压到最小（各自只有几行，且只用框架已有门面），
   但仍需在真机上各回归一次；它们的纯逻辑部分（payload 构造、分词、参数校验）已有单测覆盖。
9. **二维码不能导出图片**：产品定义稿原列了「导出图片」，实现时确认存图需要
   组件截图 + 文件/相册写入，是一条依赖多项平台能力且本机无法验证的链路，
   因此只做「复制内容 + 系统分享文本」，并在工具 limitation 里明说。
   若后续要补，建议单独排一个可上真机调试的时段。

**以下 6 条是架构重构阶段实测出来的，都属「编译通过但行为不对」这一类，交接时必须知道。**

10. **导航迁移留下了编译期看不见的缺陷**（已发现并修掉 2 处，但同类可能还有）：
    - `this.getUIContext().getRouter().back()` —— 页面 Router 的调用**类型依然合法、能编译**，
      但 Navigation 体系下它的栈是空的，按下去**没有任何反应**。
    - `Index.onPageShow` —— 页面级生命周期在 destination 出栈时**不触发**，
      原先靠它做的「返回后重读语言 / 刷新最近使用」会静默失效。
      现由 `Navigation.onNavBarStateChange(isVisible)` 兜住。
    **教训：迁移后应全仓 grep 旧的调用模式，不能只靠编译。**
    真机回归清单至少覆盖：从工具页返回、返回后页签状态、返回后「最近使用」是否更新、
    关于页入口、`GlobalNavStack` 键名、**首页页签是否真的显示出来**。

11. **增量构建会藏 ArkTS 告警**：hvigor 在源码没变时把 `CompileArkTS` 标成 UP-TO-DATE，
    那一趟**不跑 ArkTS 分析**，日志里一条告警都没有。
    实测同一份代码：增量报「entry/ 2 条」，`clean` 后全量重编报「entry/ 5 条」。
    `build.ps1` 现在会识别空转并明确提示，**不再把空转报成「告警 0 条」**。

12. **框架组件可能因为声明写错而根本不可用**，且只有 ArkTS 告警能看出来。
    实例：`NGFHdsImmersiveTabs` 把 `items` / `selectedIndex` / `onChangeCallback`
    声明成 `private`，父组件无法传入 → `items` 恒为空数组 → **页签一个都不渲染**。
    编译照过，藏了 11 轮才被第 11 条那个全量重编暴露。已按 §4 先行修正并追记 `VENDORED.md`。

13. **资源键会跨模块撞名**：app 与 HAR 定义同名键时打包「先声明者胜出」**静默覆盖**。
    实例：`about_copyright` 两边都有。`check-resources.mjs` 现在会机检这条。

14. **「从剪贴板粘贴」按钮已移除**（text-diff 工具）：读剪贴板需要
    `ohos.permission.READ_PASTEBOARD`（API 12 起），与「权限仅 INTERNET」的红线冲突；
    不声明权限时该调用必然抛异常，表现为「剪贴板为空」——一个点了没用还不报错的按钮。
    替代是系统输入框自带的长按粘贴（用户显式操作，不需 App 持权限）。
    **若决定申请该权限，恢复按钮并改回 `ToolUiKit.readClipboardText()` 即可**（代码注释里留了说明）。
